# 스크린리더 심화 가이드 (NVDA · JAWS · VoiceOver · TalkBack · 센스리더)

시각장애 사용자의 **눈을 대신하는 소프트웨어**. 자동 도구·코드 점검을 다 통과해도 실제
스크린리더에서 어색하면 의미가 없다. 국내 WA 인증 **3차 사용자 심사**가 곧 스크린리더
사용자 평가이므로, 개발자가 SR의 동작 모델을 이해하고 직접 청취하는 게 핵심이다.
(키보드 초점은 `focus-management.md`, 라이브 안내 셋업은 `router-focus.md` 참고)

---

## 1. 스크린리더 사용자는 웹을 어떻게 읽나

- **선형 읽기**: 화면을 보는 게 아니라 DOM(접근성 트리)을 **위→아래 한 줄씩** 듣는다.
  → 시각적 배치가 아니라 **마크업 순서·구조**가 경험을 결정한다.
- **빠른 탐색(quick nav)**: 전체를 다 듣지 않는다. **제목(H)·링크·랜드마크·폼·표** 단위로
  건너뛰며 훑는다 → 제목 구조와 랜드마크가 곧 "목차".
- **요소 목록**: 페이지의 제목/링크/버튼만 모아 보는 기능으로 전체 구조를 파악.
- 따라서 개발자 목표 = **의미 있는 이름 + 올바른 역할 + 논리적 구조 + 상태 안내**.

## 2. 스크린리더 × 브라우저 매트릭스 (권장 조합)

| OS | 스크린리더 | 권장 브라우저 | 비고 |
|----|-----------|--------------|------|
| Windows | **NVDA**(무료) | Chrome / Firefox | 테스트 기본. 무료라 누구나 |
| Windows | **JAWS**(유료) | Chrome | 국내외 기업/공공 점유율 높음 |
| macOS | **VoiceOver**(내장) | **Safari** | VO는 Safari와 가장 잘 맞음 |
| iOS | **VoiceOver**(내장) | Safari | 모바일 필수. 제스처 기반 |
| Android | **TalkBack**(내장) | Chrome | 모바일 필수. 제스처 기반 |
| 국내 | **센스리더**(엔비전스) | Chrome/IE | WA 3차 사용자 심사에서 흔함 |

> 최소 권장 테스트 셋: **NVDA+Chrome(데스크톱)** + **VoiceOver/iOS** 또는 **TalkBack/Android**(모바일)
> + 가능하면 **센스리더**(국내 인증 대비). SR마다 발화·지원이 달라 1개로는 부족하다.

## 3. 브라우즈 모드 vs 포커스 모드 (NVDA/JAWS 핵심 개념)

데스크톱 SR(NVDA·JAWS)에는 두 모드가 있고, 이걸 모르면 "왜 키 입력이 안 먹지?"를 오해한다.

- **브라우즈/가상 모드(Browse/Virtual)**: 읽기 탐색. 화살표·H·K 등 빠른 키로 페이지를 훑음.
  이때 일반 타이핑은 SR 명령으로 해석됨.
- **포커스/폼 모드(Focus/Forms)**: input·`role` 위젯에 들어가면 **자동 전환**되어 키 입력이
  실제 요소로 전달됨(텍스트 입력, 커스텀 위젯의 화살표 조작 등).

개발 시사점:
- **네이티브 폼 요소**(`<input>`, `<select>`)는 모드 전환이 자동으로 잘 된다 → 가능한 한 네이티브.
- 커스텀 위젯은 **올바른 `role`**(combobox, listbox, slider 등)을 줘야 SR이 포커스 모드로
  바꿔 화살표 키를 위젯에 넘긴다. role이 없으면 화살표가 브라우즈 탐색에 먹혀 위젯 조작 불가.
- VoiceOver/TalkBack은 모드 개념 대신 **제스처/로터**로 비슷한 전환을 한다.

## 4. 접근 가능한 이름(Accessible Name) 계산 — SR이 읽는 "이름"

SR이 요소를 뭐라고 읽을지는 **Accessible Name 계산 규칙**으로 정해진다. 우선순위(상위가 이김):

1. `aria-labelledby` (다른 요소 id 참조, 여러 개 가능)
2. `aria-label` (직접 문자열)
3. 요소 콘텐츠 (버튼/링크의 내부 텍스트, `<label>` 연결, `<img alt>`)
4. `title` 속성 (최후의 수단)
5. `placeholder` (input에서, 매우 약함 — 라벨 대용 ❌)

함정:
- `aria-label`은 **내부 텍스트를 덮어쓴다** → 아이콘+텍스트 버튼에 `aria-label`을 잘못 주면
  보이는 텍스트와 다르게 읽혀 혼란(+ "보이는 라벨이 이름에 포함" 위반, WCAG 2.5.3).
- `aria-labelledby`가 **존재하지 않는 id**를 가리키면 이름이 **빈값** → 버튼이 "버튼"으로만 읽힘.
- 장식 아이콘은 `aria-hidden="true"`로 이름 계산에서 제외.
- 검증: DevTools 접근성 패널 / cmux로 `computedName` 확인(`SKILL.md` §3-5).

## 5. 라이브 리전(Live Region) — SR별 동작 차이

비동기 변화(토스트·검색결과·오류)를 SR에 알리는 유일한 표준 수단(→ `router-focus.md` LiveAnnouncer).

- `aria-live="polite"`: 현재 읽기 끝난 뒤 안내(일반).
- `aria-live="assertive"` / `role="alert"`: 즉시 끼어들어 안내(오류·긴급).
- `role="status"`(=polite), `role="alert"`(=assertive)는 암묵적 live.

주의(SR별 편차 큼):
- 라이브 영역은 **페이지 로드 시 이미 DOM에 존재**해야 안정적으로 동작 → 나중에 통째로
  삽입하면 첫 메시지를 놓친다. 빈 컨테이너를 미리 두고 **내용만 갱신**.
- 같은 문자열을 연속으로 넣으면 안 읽히는 SR이 있다 → 비우고 다시 넣기(LiveAnnouncer 패턴).
- `aria-atomic="true"`: 영역 전체를 다시 읽음. 부분 갱신만 읽히길 원하면 `false`.
- VoiceOver/모바일은 polite 무시·지연이 잦다 → 중요한 건 초점 이동까지 병행 고려.

## 6. 모바일 스크린리더 — VoiceOver(iOS) / TalkBack(Android)

모바일은 **제스처 기반**이라 데스크톱과 상호작용 모델이 다르다. "모바일/PC" 둘 다 목표면
반드시 실기기 테스트.

### 공통 동작 모델
- **한 손가락 스와이프(좌/우)**: 이전/다음 요소로 **순차 이동**(= 모바일판 Tab).
- **한 손가락 떼지 말고 이동**: 임의 탐색(손가락 닿는 요소 읽기).
- **한 손가락 더블탭**: 활성화(클릭).
- **스크롤**: **TalkBack = 두 손가락 쓸기**(움직인 만큼) / **VoiceOver = 세 손가락 쓸기**(페이지 단위).
- **로터(VoiceOver) / 탐색 설정(TalkBack)**: 제목·링크·폼 단위 빠른 탐색 모드 전환.

> 국내 **앱 접근성 심사 기준 스크린리더 = TalkBack**(삼성 구버전 Voice Assistant 아님). 정확한
> 제스처표·네이티브 초점 API·MACAG 18항목은 **`macag` 스킬**(`/macag`) 참고.

### 모바일 특화 개발 주의
- **터치 타깃 ≥ 44×44**(`mobile-responsive.md`) — 작으면 더블탭 활성화 어려움.
- **스와이프 순서 = DOM 순서**: 시각 배치와 어긋나면 모바일에서 더 치명적.
- **커스텀 제스처와 SR 제스처 충돌**: 스와이프로 동작하는 UI는 SR 켜면 스와이프가 탐색에
  쓰여 작동 안 함 → **단일 포인터 대체 조작**(KWCAG #21) 필수.
- `aria-hidden="true"`로 가린 영역은 모바일 SR에서도 스와이프로 안 닿게(모달 배경 등).
- **포커스 가능 순서**: 모달 열면 모바일 SR 초점도 모달로 이동시켜야(focus + `aria-modal`).
- TalkBack은 일부 ARIA role 지원이 데스크톱보다 제한적 → **네이티브 시맨틱 우선** 원칙이 더 중요.
- 하이브리드 앱(WebView)은 WebView 내부 웹 접근성 + 네이티브 셸 `contentDescription`/
  `accessibilityLabel` 둘 다(→ 네이티브는 **`macag` 스킬**).

## 8. 흔한 스크린리더 문제 패턴 → 해결

| 증상(SR에서) | 원인 | 해결 |
|--------------|------|------|
| "버튼"이라고만 읽힘 | 아이콘 버튼에 이름 없음 | `aria-label` 부여, 장식 아이콘 `aria-hidden` |
| 같은 내용 두 번 읽힘 | alt + 인접 텍스트 중복 / aria-label + 내부텍스트 | 한쪽 제거, 장식은 `alt=""` |
| 링크가 "링크 링크 링크" | 텍스트 없는 반복 링크 | 의미 있는 텍스트/`aria-label` |
| 폼 필드 이름 안 읽힘 | 라벨 미연결 | `<label for>` / `aria-labelledby` |
| 화살표로 위젯 조작 불가 | role 없어 포커스 모드 전환 안 됨 | 올바른 `role` + roving tabindex(`focus-management.md`) |
| 모달인데 배경까지 읽힘 | 배경 비활성화 안 함 | `inert` / 배경 `aria-hidden` + 초점 트랩 |
| 토스트/오류 안 읽힘 | 라이브 리전 없음/늦게 삽입 | 사전 배치된 `aria-live` 영역 갱신 |
| 숨김 텍스트가 화면에 보임 | `display:none`이 아닌 잘못된 숨김 | 시각만 숨김은 `.sr-only` 클립 기법 |
| 보이는데 SR이 못 읽음 | `aria-hidden="true"` 오용 / `display:none` | 잘못된 hidden 제거 |

`.sr-only`(시각만 숨기고 SR엔 읽힘) 표준 패턴은 `router-focus.md` 참고.

## 9. 무료로 시작하는 테스트 환경 셋업

- **Windows**: [NVDA](https://www.nvaccess.org/) 설치(무료) → Chrome로 사이트 열고 NVDA+↓로 통독.
- **Mac**: 설정 없이 **Cmd+F5**로 VoiceOver 즉시 시작 → Safari 권장.
- **iPhone**: 설정▸손쉬운 사용▸VoiceOver, 단축키(측면 삼중클릭) 등록 → 스와이프 탐색.
- **Android**: 설정▸접근성▸TalkBack 켜기 → 음량키 단축키 등록.
- 끄는 법을 먼저 익혀라(Mac Cmd+F5, 모바일 단축키) — 안 그러면 조작이 막힌다.

## 10. 청취 테스트 체크리스트 (출시·인증 전)

`manual-testing.md`의 시나리오를 SR별로 1회씩:
- [ ] 제목(H)만으로 페이지 목차가 논리적으로 들리나
- [ ] 모든 이미지/아이콘/버튼/링크가 **의미 있는 이름**으로 읽히나(빈 이름·중복 없음)
- [ ] 폼: 라벨·필수·설명·오류가 빠짐없이 들리고, 오류 시 초점/안내가 되나
- [ ] 동적 변화(검색결과 수·토스트·로딩 완료)가 라이브 리전으로 들리나
- [ ] 모달: 열림 안내 + 배경 미읽힘 + 닫을 때 복귀(`focus-management.md`)
- [ ] 커스텀 위젯(탭·메뉴·콤보박스)이 화살표로 조작되고 상태가 읽히나
- [ ] **모바일 SR**(VoiceOver/TalkBack)에서 스와이프 순서·더블탭 활성화·제스처 충돌 없는가
- [ ] SPA 라우팅이 SR에 전환으로 들리나(`router-focus.md`)
- [ ] (가능 시) 센스리더로 국내 인증 환경 점검

> 자동 도구는 이 중 30~40%만 검출한다. **나머지는 이 청취 테스트로만** 확인 가능.
